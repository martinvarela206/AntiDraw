# Project Specific Rules (AntiDraw)

This file contains rules specific to the AntiDraw vector graphics editor extension for VS Code. Rules are written in English to optimize context window efficiency and reduce token usage.

---

## Operational Execution

1. **Project Prompt Acknowledgment**:
   - Every response must explicitly include: `Project Prompt Loaded.` right after the Markdown Prompt acknowledgment.

---

## Build, Packaging & Companion Metadata

2. **Mandatory VSIX Generation & Packaging**:
   - After completing code modifications and updating the project version for each atomic item, always build and package the extension into a `.vsix` artifact (`pnpm run package` / `vsce package --no-dependencies`).

3. **Strict SVG Standard Cleanliness & Companion JSON Metadata Isolation**:
   - Output SVG documents generated by AntiDraw (`SvgSerializer.toSvgString()`) MUST adhere strictly to clean, standard W3C SVG specifications.
   - NEVER serialize non-standard attributes, proprietary flags, or private metadata prefixes (`data-shape`, `data-parametric`, `data-corner-*`, `data-node-types`, `data-ellipse-type`, `data-inner-ratio`, `data-gradient`, `data-filter-shadow`, etc.) directly into SVG XML element tags.
   - All non-standard parametric geometry states, vertex metadata, gradient locks/settings, shadow configurations, and editor parameters MUST be persisted exclusively to the companion `.json` metadata file mapped to the SVG document (under `metadata.elements[elId] = { ... }`).
   - When loading an SVG (`SvgDeserializer.loadSvgString()`), reconstruct and rehydrate full editor state by fusing standard SVG markup with its companion `.json` metadata.

---

## Architecture, Componentization & Parity

4. **AntiDraw Componentization & Refactoring Prioritization**:
   - Every feature, UI panel, tool handler, interaction controller, and engine subsystem must remain strictly modular and componentized.
   - If any component, class, or handler grows too large, acquires excessive complexity, or violates single-responsibility principles, a dedicated refactoring task MUST immediately be added and prioritized in `Docs/TODO.md`.

5. **Universal Element & Tool Parity for Shared Behaviors**:
   - Whenever a bug, defect, or requirement is identified for an interaction, snapping behavior, handle manipulation, or visual feedback on an element or tool:
     - You MUST NOT patch only that specific element or tool in isolation.
     - You MUST audit and enforce consistent, identical behavior across ALL parallel and related elements (circles, ellipses, arcs, pies, donuts, rectangles, stars, regular polygons, freeform paths) and across ALL tools and interaction controllers (NodeTool, SelectTool, TranslateInteraction, TransformInteraction, Scale, Rotate).
     - Any capability or fix applied to one handle, anchor, or landmark must be universally integrated across all handles, anchors, and landmarks.

6. **AntiDraw Architectural Anti-Regression Safeguards**:
   - **Prototype & Getter Preservation**: Never use shallow object spreads (`{ ...this }`, `Object.assign({}, instance)`) when passing manager or service contexts to engines or sub-handlers. Spread syntax strips prototype getters (such as `get grids()`, `get guides()`), resulting in silent `undefined` values and catastrophic feature loss without compile-time errors. Always pass instance references directly or map properties explicitly.
   - **Decoupling Presentation from Computation**: Algorithmic services (snapping calculations, geometric transforms, hit-testing, projection) must never condition their execution on visual presentation flags (e.g., coupling `snapToGrid` to `showGrid`) unless specifically dictated by design specifications.
   - **Event Cascade & Hit-Testing Precedence Invariants**: When adding interactions, handlers, or bounding-box modes, ensure new event listeners or hit tests do not swallow, shadow, or preempt base interactions (canvas dragging, node selection, element translation) without fallback delegation.
   - **Universal Consumer Audit on Shared Contracts**: When altering shared interfaces, context contracts (`ToolContext`, `SnappingContext`), or services (`HistoryService`, `CanvasManager`), inspect all consumer tools and handlers to guarantee complete operational parity and zero regression.

## Multi-Item Prompt Decomposition & Atomic Loop Execution

7. **Mandatory Decomposition of Multi-Item Prompts**:
   - Whenever the prompt or active TODO list contains multiple tasks, bullet points, fixes, additions, or removals (2 or more distinct items):
     - **NEVER** bundle, combine, or resolve multiple items together in a single step, file edit block, version bump, or commit.
     - You MUST immediately decompose the work into an ordered list of individual, discrete items.
     - Evaluate and classify each item individually before executing it:
       - If the feature already exists partially, or has defects/modifications: classify as `fix`.
       - If the capability is completely new and did not exist before: classify as `feat`.

8. **Strict Sequential Atomic Execution Loop**:
   - Execute items sequentially, one by one, completing the entire cycle for each item before touching the next:
     1. **Implement Code**: Make code changes strictly for the single active item.
     2. **Update Documentation**:
        - **Clean `Docs/TODO.md`**: Follow `project-docs-rules.md` to completely delete/remove completed items (never leave `[x]`).
        - **Update Catalog**: Update `Docs/Descripción de las herramientas.md` with relevant functional details for this item.
     3. **Version Bump**: Increment `package.json` (`patch` for `fix`, `minor` for `feat`) following the SemVer rule in `general-rules.md`.
     4. **Build & Package**: Run `pnpm run package` to compile and create the `.vsix` artifact for that specific version.
     5. **Atomic Commit**: Stage files and commit with simple conventional format in Spanish:
        - `fix: <elemento o problema corregido en español>`
        - `feat: <nuevo elemento o funcionalidad añadida en español>`
     6. **Advance to Next Item**: Only after the commit has been successfully created, proceed to the next item in the prompt list and repeat steps 1 to 5.
   - In the final response, provide a distinct verification checklist grouped by each atomic commit for user testing.
